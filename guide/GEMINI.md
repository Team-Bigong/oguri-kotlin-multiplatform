# Oguri Server - Gemini Development Guide

> 이 문서는 Oguri 서버 모듈에서 AI(Gemini)가 코드를 제안하거나 수정할 때 반드시 따를 기준을 정의한다.

> 나는 Kotlin + Spring Boot 기반 서버 개발자이며,코드는 "동작하는 코드"가 아니라 **"운영 가능한 코드"**여야 한다.

------------------------------------------------------------------------

## 1. 기본 철학

-   요청된 문제만 해결한다.
-   수정은 최소 범위로 한다.
-   기존 구조를 존중한다.
-   불필요한 추상화, 리팩터링, 구조 변경은 하지 않는다.
-   설계 변경이 필요하면 반드시 먼저 이유를 설명한다.

코드는 우아하되 과시적이면 안 된다.

------------------------------------------------------------------------

## 2. 기술 스택 및 아키텍처

-   Kotlin
-   Spring Boot
-   Gradle (KTS)
-   JPA (QueryDSL 사용 가능)
-   Layered Architecture

Controller → Service → Repository

-   Controller: 요청/응답 매핑
-   Service: 비즈니스 로직 + 트랜잭션
-   Repository: 데이터 접근 전용

비즈니스 로직은 Repository에 두지 않는다.

------------------------------------------------------------------------

## 3. 코드 수정 원칙 (매우 중요)

### 3.1 최소 수정 원칙

-   전체 파일 재작성 금지
-   기존 로직 보존
-   필요한 부분만 정확히 수정
-   import 정리 등 불필요한 변경 금지
-   함수 시그니처 변경 금지 (요청 없는 한)

문제 해결이 목적이지 구조 개선이 목적이 아니다.

### 3.2 안정성과 운영 고려

-   Null 안전성 고려
-   예외 처리 누락 금지
-   트랜잭션은 Service 계층에서만 사용
-   로그는 의미 있게 남긴다
-   테스트를 깨뜨리지 않는다
-   성능 영향이 있다면 반드시 명시한다
-   N+1 가능성 항상 고려한다

------------------------------------------------------------------------

## 4. 응답 스타일

-   모든 설명은 한국어로 작성한다.
-   불확실하면 추측하지 않는다.
-   모르면 모른다고 말한다.
-   설계 변경이 필요하면 먼저 질문한다.
-   대안이 있으면 장단점을 설명한다.

------------------------------------------------------------------------

## 5. 금지 사항

-   과도한 리팩터링
-   전역 설정 변경
-   빌드 설정 대규모 수정
-   의존성 추가 (요청 없는 경우)
-   불필요한 디자인 패턴 도입
-   헥사고날/DDD 풀구조 전환
-   멀티 모듈 구조 변경

------------------------------------------------------------------------

## 6. 코드 스타일

-   명확한 변수명 (축약어 금지)
-   Early return 선호
-   불필요한 nullable 지양
-   Entity 직접 반환 금지
-   확장 함수 남용 금지
-   단순 변환은 Service에서 처리 (별도 Mapper 분리하지 않음)

------------------------------------------------------------------------

## 7. 예외 처리

-   RuntimeException 남발 금지
-   기존 커스텀 예외가 있으면 그것을 사용
-   HTTP 상태 코드 명확히 구분
-   GlobalExceptionHandler가 있다면 활용

------------------------------------------------------------------------

## 8. 성능 원칙

-   N+1 문제 고려
-   불필요한 객체 생성 지양
-   컬렉션 처리 시 시간 복잡도 고려
-   Fetch 전략은 의도를 명확히 설명
-   캐시는 근거 기반으로만 제안

------------------------------------------------------------------------

## 9. DB 원칙

-   트랜잭션은 Service에서 관리
-   Repository는 비즈니스 로직을 가지지 않는다
-   QueryDSL은 복잡한 동적 조건일 때만 사용
-   Flyway 사용
-   이미 적용된 마이그레이션 수정 금지

------------------------------------------------------------------------

## 10. 최종 기준

코드는 "멋있게"가 아니라\
**"10년 후에도 읽힐 수 있게"** 작성한다.

나는 시니어 개발자다.\
단순하지만 견고한 코드를 선호한다.

------------------------------------------------------------------------

# 11. 프로젝트 컨텍스트 (Oguri)

Oguri는 **여행지 추천 API 서버**이다.

모바일 앱에 데이터를 제공하는 서버이며, View 렌더링은 하지 않는다.

### 핵심 도메인

#### Place

-   country
-   city
-   summary
-   description
-   recommendStartMonth (Int)
-   recommendEndMonth (Int)
-   distanceKm
-   averageBudget
-   bigMacIndex
-   createdAt / updatedAt

추천 기간은 문자열이 아니라 startMonth / endMonth 정수 컬럼으로
관리한다.

#### PlaceImage

-   Place와 1:N 관계
-   displayOrder로 정렬
-   isThumbnail 필드 존재
-   응답 시 List`<String>`{=html} 형태로 반환

이미지 URL을 문자열로 합쳐 저장하지 않는다.\
별도 테이블로 정규화한다.

------------------------------------------------------------------------

# 12. 프로젝트 폴더 구조 기준

단순한 Layered 구조를 유지한다.

com.oguri.server\
├─ controller\
├─ service\
├─ repository\
├─ domain\
├─ dto\
├─ config\
├─ exception\
└─ util (필요 시)

### 구조 원칙

-   feature 단위 패키지 재구성 금지
-   domain/application/infrastructure 분리 금지
-   mapper 패키지 분리 금지
-   Entity는 domain에 위치
-   DTO는 dto 패키지에 위치

예시 (Place):

controller/PlaceController.kt\
service/PlaceService.kt\
repository/PlaceRepository.kt\
domain/Place.kt\
domain/PlaceImage.kt\
dto/PlaceResponse.kt

파일 이동 및 패키지 구조 변경은 하지 않는다.
