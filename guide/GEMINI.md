# Oguri Server - Gemini Development Guide

이 문서는 Oguri 서버 모듈에서 AI(Gemini)가 코드를 제안하거나 수정할 때 반드시 따를 기준을 정의한다.

나는 Kotlin + Spring Boot 기반 서버 개발자이며,
코드는 "동작하는 코드"가 아니라 "운영 가능한 코드"여야 한다.

---

## 1. 기본 철학

- 과한 리팩터링을 하지 않는다.
- 요청된 문제만 해결한다.
- 기존 구조를 존중한다.
- 수정은 최소 범위로 한다.
- 불필요한 추상화는 추가하지 않는다.
- 설계 변경이 필요한 경우 반드시 먼저 이유를 설명한다.

코드는 우아해야 하지만, 과시적이면 안 된다.

---

## 2. 기술 스택

- Language: Kotlin
- Framework: Spring Boot
- Build: Gradle (KTS)
- Database: (JPA / QueryDSL 가능성 고려)
- Architecture: Layered Architecture (Controller → Service → Repository)

---

## 3. 코드 수정 원칙 (매우 중요)

### 3.1 최소 수정 원칙

- 전체 파일을 다시 작성하지 않는다.
- 기존 로직을 보존한다.
- 필요한 부분만 정확히 변경한다.
- import 정리, 포맷 변경 등 불필요한 수정은 하지 않는다.
- 함수 시그니처를 바꾸지 않는다 (요청이 없는 한).

문제 해결이 목적이지, 구조 개선이 목적이 아니다.

---

### 3.2 안정성 우선

- Null 안전성 고려
- 예외 처리 누락 금지
- 트랜잭션 경계 명확히
- Side effect 발생 가능성 설명

---

### 3.3 운영 환경 고려

- 로그는 의미 있게 남긴다.
- 보안 관련 설정은 함부로 완화하지 않는다.
- 테스트 코드가 있다면 깨지지 않게 한다.
- 성능에 영향을 줄 수 있는 변경은 반드시 언급한다.

---

## 4. 응답 스타일

- 모든 설명은 한국어로 작성한다.
- 불확실한 내용은 추측하지 않는다.
- 모르면 모른다고 말한다.
- 설계 변경이 필요하면 먼저 질문한다.
- 대안이 여러 개라면 각각의 장단점을 설명한다.

---

## 5. 금지 사항

- "이렇게 바꾸는 게 더 좋아 보입니다" 식의 과도한 리팩터링
- 전역 설정 변경
- 빌드 설정 대규모 수정
- 의존성 추가 (요청 없는 경우)
- 불필요한 디자인 패턴 도입

---

## 6. 선호 스타일

- 명확한 변수명
- 의미 있는 함수 분리
- Early return 선호
- 불필요한 nullable 지양
- 데이터 클래스 적극 활용
- 확장 함수는 남용하지 않는다

---

## 7. 예외 처리 기준

- RuntimeException 남발 금지
- 커스텀 예외가 이미 존재하면 그것을 사용
- HTTP 상태 코드는 명확히 구분
- GlobalExceptionHandler가 있다면 활용

---

## 8. 성능 원칙

- N+1 문제 가능성 항상 고려
- 불필요한 객체 생성 지양
- 컬렉션 처리 시 시간 복잡도 고려
- 캐시 사용 여부는 근거 기반으로 제안

---

## 9. DB 관련

- 트랜잭션은 Service 계층에서 관리
- Repository는 비즈니스 로직을 가지지 않는다
- Fetch 전략은 명확하게 의도 설명
- 쿼리 변경 시 실행 SQL 영향 고려

---

## 10. 최종 기준

코드는 “멋있게”가 아니라
“10년 후에도 읽힐 수 있게” 작성한다.

나는 시니어 개발자다.
단순하지만 견고한 코드를 선호한다.
