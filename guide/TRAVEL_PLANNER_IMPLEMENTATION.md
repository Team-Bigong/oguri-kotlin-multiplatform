# 여행 플래너 구현 계획

버전: 1.0 · 작성일: 2026. 11. 13. · 상태: 구현 전 기술 계획

[통합 명세 v0.3](./TRAVEL_PLANNER_SPEC.md)는 제품의 동작과 AC01–AC22를, [디자인 명세](./TRAVEL_PLANNER_DESIGN.md)는 화면과 조작을 정의한다. 이 문서는 두 명세를 코드로 옮기는 순서와 책임, 저장·동기화 계약, 단계별 완료 기준을 정한다. 현재 구조는 로컬 `develop-mobile`의 `7414f51`과 작업본에서 확인했다. 아래의 새 파일명·API·데이터 모델은 구현안이며, 빌드나 운영 환경에서 확인한 결과가 아니다.

**첫 개발 목표는 로그인한 사용자가 여행을 만들고, 장소 하나를 날짜에 담아 저장한 뒤 앱을 다시 열어 확인하는 것이다.** 목록에서 이 흐름을 먼저 완성하고 지도·검색, 기존 화면 연결, 공동 편집을 차례로 붙인다. 초기 단계는 내부 확인용이다. 공개 MVP에는 통합 명세대로 공동 편집, 관리, 선택형 출발 전 알림까지 포함한다.

**P0에서 남길 결과:** ① Android·iOS에서 Google 지도 한 화면에 핀 두 개·연결선·목록을 띄운 결과, ② 도시 검색·현지 시간대·출처 표시·저장 가능 필드 확인, ③ 초대용 HTTPS 도메인·앱 서명과 설치 전후 링크 확인 방법, ④ 개발용 PostgreSQL·테스트 계정·양 플랫폼 빌드 기준선이다. 푸시 자격 증명과 실제 기기 전달은 일찍 확인하되 알림 구현은 P6에서 한다. 외부 계정·키·도메인 설정이 없는 항목은 실제 결과를 추정하지 않는다. 해당 연동만 미검증으로 두고 목록·저장 작업은 진행할 수 있다.

## 2. 구현 순서와 완료 기준

각 단계는 기능을 직접 실행해 확인할 수 있는 변경 단위다. 기반 파일을 모두 만들어 놓고 UI를 마지막에 붙이지 않는다. 먼저 테스트 계정 또는 개발용 설정에서만 새 진입을 연다.

| 단계 | 개발 작업 | 다음 단계로 넘어가는 기준 |
| --- | --- | --- |
| **P0 · 연동 검증** | 지도·Places·시간대·링크를 작은 실험으로 확인하고 프로젝트 빌드 기준선을 기록한다. 지도 구현 후보 중 양 플랫폼에서 검증된 방식을 고른다. | 사용 가능한 SDK 경로, 출처·보관 제한, 필요한 설정과 미확인 항목을 기록한다. 실험 코드는 공개 진입에 연결하지 않는다. |
| **P1 · 개인 계획 저장** | Flyway 초기 테이블, 여행 생성·목록·조회·방문 편집 API, 모바일 저장소와 T01·T02·T03 목록·T05를 연결한다. 기존 도시 또는 개발용 도시 데이터로 시작하고 직접 추가·날짜 배정·시각·메모·삭제·순서 이동을 검증한다. | 새 여행을 만들고 장소를 저장한 뒤 재실행·다른 로그인 기기에서 같은 계획을 본다. 같은 생성·추가 요청을 반복해도 한 번만 반영되고 다른 계정은 읽거나 쓸 수 없다. |
| **P2 · 장소와 지도** | T04 도시·장소 검색, 검색 결과 추가, Google 지도, 날짜·핀·목록 선택, 드래그, 외부 길찾기를 연결한다. T02에 추천 밖 도시와 시간대 선택을 붙인다. | 양 플랫폼에서 같은 방문이 목록과 지도에 반영된다. 날짜 없음·겹친 핀·좌표 없음·지도 및 검색 실패에서도 목록과 기존 계획이 남는다. |
| **P3 · 오구리 진입과 복귀** | 도시·기간 상세, 마이페이지 내 여행, 홈 이어보기, 지난 여행의 다음 휴가 찾기, 생성·초대용 로그인 복귀를 연결한다. | 추천의 문맥이 전달되고 실제 날짜를 바꿀 수 있다. 로그인 취소·가입·외부 지도 왕복 뒤에도 작업을 잃지 않는다. 홈 추천·북마크·세 탭·연차 계산은 기존과 같이 동작한다. |
| **P4 · 공동 편집과 관리** | T06·T07 초대/참여, 권한, 온라인 변경 반영, 최근 변경, 기간·도시 수정, 소유권 이전, 나가기·삭제, 계정 제거를 구현한다. | 두 계정으로 독립 수정 보존, 같은 대상 충돌, 동시 참여, 제외·철회·탈퇴를 검증한다. 공용 데이터가 두 기기에서 같은 결과로 수렴한다. |
| **P5 · 복구와 사용감** | 계정별 초안 복구, 인증 만료·권한 종료, 실패별 재시도, 안전한 되돌리기, 접근성, 네 언어·라이트/다크, 광고·분석 개인정보 경계를 마무리한다. | 연결 중단·재실행·계정 전환 뒤 입력·확정 상태·권한이 섞이지 않는다. 큰 글자·스크린리더에서 지도나 드래그 없이 계획을 편집할 수 있다. |
| **P6 · 선택 알림** | T07의 개인 예약, 서버 발송·취소, Android·iOS 기기 등록과 알림 진입을 연결한다. | 신청·거절·취소·기간 변경·계정 변경·권한 종료를 실제 기기에서 확인한다. 이전 예약이 새로 발송되지 않으며 기본값은 꺼짐이다. |
| **P7 · 출시 전 통합 검증** | 서버·모바일·링크 배포 호환, AC01–AC22, 사용감 과업, 사용량 한도·비용·오류·리텐션 집계를 검증한다. | 인수 사례별 실행 증거와 남은 결함을 기록한다. 미해결 필수 항목이 있는 상태를 공개 MVP 완료로 표시하지 않는다. |

**바로 시작할 첫 변경:** P1에서 `여행 생성 → 내 여행에서 열기 → 직접 장소를 첫날에 추가 → 새로 열어 확인`까지만 한 번에 잇는다. 같은 변경에 비회원 차단, 다른 회원의 접근 차단, 중복 생성·추가 검증을 포함한다. 그다음 P1의 편집 동작을 작은 변경으로 이어 붙인다. P0의 지도·링크·알림 결정을 기다릴 필요가 없다.

## 3. 코드 위치와 역할

모바일의 의존성은 `data → domain ← feature/ui`다. `domain`은 UI·data·플랫폼 레이어를 가져오지 않고, `data`는 UI를 가져오지 않는다. `AppGraph`가 구현체를 주입한다. [모바일 구조](./MOBILE_PROJECT_STRUCTURE.md)·[규칙](./MOBILE_CONVENTIONS.md)·[코드 스타일](./MOBILE_CODE_STYLE.md)을 따른다.

| 위치 | 추가하거나 수정할 내용 |
| --- | --- |
| `composeApp/src/commonMain/kotlin/com/bigong/oguri/domain/{model,repository,usecase}` | `TravelPlan`, `TravelDates`, `TravelVisit`, `TravelPlanRepository` 등. 여행 읽기·생성·방문 변경처럼 역할이 분명한 행동을 노출한다. 장소 조회는 `TravelPlaceSearchRepository`로 분리한다. |

| `server/src/main/kotlin/com/bigong/oguri/{controller,service,domain,repository,dto}` | `TravelPlanController`, `TravelPlanService`, 여행·방문·멤버십 Entity와 조회, 명령 DTO. 공동 편집에서 초대·알림 책임이 생기면 해당 서비스만 추가한다. Controller는 매핑과 인증 주체 전달, Service는 권한·트랜잭션, Repository는 조회·저장을 맡는다. |

서버에서는 [서버 가이드](./GEMINI.md)의 layered 구조와 JPA Entity를 유지한다. 날짜 유효성·기간 이동·방문 배정·소유권 같은 규칙은 값을 읽어 Service가 다시 판단하기보다 해당 객체의 행동으로 표현한다. Service는 권한 확인, 잠금, 여러 객체의 변경과 커밋을 조율한다. Entity를 그대로 API에서 반환하지 않는다. 이후 영속성과 독립된 규칙을 별도로 공유할 필요가 확인되면 해당 값과 규칙만 분리하는 안을 검토한다.

[Android 공식 도메인 가이드](https://developer.android.com/topic/architecture/domain-layer)는 선택적 domain이 data의 repository에 의존하는 구성을 설명한다. 이 프로젝트는 **repository 인터페이스를 domain에 두고 data가 구현하는 방식**을 채택한다. 공식 권장의 단방향 상태 흐름·생명주기 기반 수집은 적용한다. [UI 상태 권장 사항](https://developer.android.com/topic/architecture/recommendations)에 맞춰 저장 결과·충돌·인증 복귀를 유실 가능한 이벤트에만 두지 않는다. 기존 `SideEffect` 관례는 순간적인 햅틱이나 외부 화면 열기처럼 누락 시 계획 데이터가 바뀌지 않는 효과에 한정한다.

## 4. 도메인과 데이터 저장

먼저 행동을 정한다. `여행을 만든다 → 날짜에 방문을 담는다 → 방문을 옮긴다 → 항목을 수정한다 → 참여를 허용하거나 끝낸다`의 책임을 나눈다. 서버가 규칙과 확정 순서의 기준이며 모바일 검증은 빠른 안내를 위한 것이다. 임의의 `saveTrip(payload)`처럼 모든 데이터를 덮어쓰는 인터페이스는 노출하지 않는다.

| 모델·저장 후보 | 지킬 규칙 |
| --- | --- |
| `travel_plans` · 여행 | 실제 시작·종료일, 기준 도시, 확인한 IANA 시간대, 제목, 소유자, 추천 출처 참조. `startDate ≤ endDate`, 당일 허용. 개인 연차·추천 계산 결과는 멤버 응답에 포함하지 않는다. |
| `travel_plan_members` · 멤버십 | 여행과 회원의 조합은 하나만 존재한다. 소유자도 참여자이며 소유자 판정의 원본은 여행의 소유자 필드 하나다. 참여를 끝내도 공동 계획의 방문은 유지한다. |
| 날짜 그룹·`travel_visits` · 방문 | 날짜 그룹은 시작일 기준 일차와 미배정으로 구분한다. 방문 ID·정렬 위치·선택 현지 시각·메모·직접 입력 이름/위치·공급자 장소 ID를 구분한다. 같은 장소의 재방문은 다른 방문 ID이며 목록 키도 그 ID다. |
| 변경 순번·일차 순서 버전 | 여행 변경 순번은 갱신 여부·최근 변경의 기준이다. 날짜·도시·시간대 변경에는 구조 버전, 순서에는 해당 일차/미배정 그룹 버전을 사용한다. 버전이 다른 세 범위를 구별해 독립된 수정을 함께 저장한다. |
| 변경 요청 기록·요약 | 요청 ID·요청 내용의 지문·확정 결과 식별자와 순번을 저장해 중복 반영을 막는다. 최근 변경은 날짜·종류·대상 식별에 필요한 값만 보관한다. 메모 본문이나 공급자 상세 응답을 이력으로 복제하지 않는다. |
| 초대·이전·알림 | P4에서 초대 만료/철회·이전 수락 상태·개인 최근 변경 확인 범위, P6에서 개인 예약·기기 연결을 추가한다. 실제 사용할 단계에 새 migration을 추가한다. |

실제 날짜는 `LocalDate`, 방문 시각은 선택 `LocalTime`, 발송·기록 시점은 `Instant`로 구분한다. 시간대가 불명확하면 기기 설정으로 대체하지 않는다. 일차는 상대 위치를 저장하므로 시작일이 바뀌어도 방문 순서는 유지한다. 기간 단축은 영향 미리보기 후 범위 밖 방문을 미배정으로 옮기며, 도시·시간대 변경은 현지 시각 보존을 설명한다. 미리보기와 적용 사이에 버전이 바뀌면 다시 확인한다.

추천 출처에는 진입 유형과 확인된 도시·추천 날짜를 별도로 남긴다. [DefaultCalendarRepository.kt](../composeApp/src/commonMain/kotlin/com/bigong/oguri/data/repository/DefaultCalendarRepository.kt)의 `CalendarPeriod.id`는 페이지와 목록 위치에서 계산하므로 영속 식별자로 쓰지 않는다. 추천이 바뀌거나 북마크를 해제해도 여행이 바뀌지 않는다.

여행의 기간 이동·순서 변경·멤버 제외처럼 여러 행을 바꾸는 작업은 한 트랜잭션으로 끝낸다. 같은 여행의 편집은 짧은 여행 행 잠금으로 직렬화하는 안을 기본으로 하고, 잠금 안에서 권한·버전·대상 존재를 다시 확인한다. 순번 배정·변경 요약·중복 방지 기록도 함께 커밋한다. 지도 조회와 푸시 전송은 여행 편집 트랜잭션 밖에서 한다. [PostgreSQL 잠금 문서](https://www.postgresql.org/docs/current/explicit-locking.html)를 참고해 계정 제거와 여러 여행 잠금의 순서를 정하고 실제 PostgreSQL에서 경합을 검증한다.

여행/회원 목록, 일차별 방문 순서, 여행별 변경 순번, 예약 시각에는 사용 쿼리에 맞춰 인덱스를 둔다. 순서의 중복 방지와 재정렬 갱신이 동시에 성립하는지 검증한다. Flyway 번호는 구현 시 실제 브랜치의 최신 버전 다음으로 잡는다. 새 DB와 기존 스키마에서 모두 올릴 수 있어야 하며 적용된 migration은 수정하지 않는다.

## 5. 서버 API와 동시 편집 계약

아래 경로는 구현 제안이다. 기존 API와 같은 `/api/v1`을 사용한다. 계약을 먼저 고정하고 `server`의 응답과 Ktor DTO가 같은 예제 요청으로 통과하도록 맞춘다.

| 동작 | 제안 경로·계약 |
| --- | --- |
| 여행 생성·목록 | `POST /api/v1/trips`, `GET /api/v1/trips`. 서버 인증 주체를 소유자로 사용한다. 목록은 요약·기간·상태만 전달한다. |
| 일정 조회·갱신 확인 | `GET /api/v1/trips/{tripId}`. 일정과 변경 순번을 반환하고, 같은 순번의 조건부 요청에는 권한을 다시 확인한 뒤 `304`를 반환할 수 있다. 공용 캐시에 저장하지 않는다. |
| 여행·방문 변경 | `POST /api/v1/trips/{tripId}/commands`. `AddVisit`, `EditVisit`, `ReorderDay`, `RemoveVisit`, `UpdateTripDetails`, `UndoVisitChange` 등 허용된 명령을 검증한다. 명령마다 필요한 대상·기준 버전·수정 필드만 받는다. |
| 공동 변경 | `GET /api/v1/trips/{tripId}/changes`와 확인 범위 저장. 서버는 사용자가 실제 열어 본 순번까지만 전진시키고, 읽는 중 들어온 변경은 다음 확인에 남긴다. |
| 초대·관리 | 여행 아래의 초대 발급·철회, 멤버 제외·나가기, 소유권 이전·수락, 전체 삭제를 소유자/참여자 역할에 맞게 분리한다. 초대 미리보기와 참여는 `POST /api/v1/trip-invites/preview`, `POST /api/v1/trip-invites/join`으로 분리해 비밀값을 요청 본문에서 전달한다. |
| 장소 조회·알림 | 도시/장소 조회는 `/api/v1/travel-places` 아래에 분리한다. 비회원의 생성 전 도시 검색은 입력을 막지 않되 별도 요청 제한을 둔다. 방문 장소 검색은 회원·여행 권한을 확인한다. 알림은 여행 아래에 본인 예약 조회·설정·해제를 둔다. |

- **인증과 권한:** 새 여행 API는 기본적으로 비회원을 차단하고, 필요한 도시 검색과 유효한 링크의 제한된 미리보기만 예외로 둔다. 유효한 토큰을 받았어도 해당 회원이 아직 존재하며 접근 권한이 있는지 서버에서 확인한다. 세션 없음·만료는 `401`, 확인된 권한 부족은 `403`, 존재를 알려 줄 수 없는 여행은 `404`로 구분한다. 삭제·만료·철회 상태는 알려 줘도 되는 요청에만 구별한다. HTTP 상태와 안정된 오류 코드로 분기하고 서버 예외 문구를 그대로 사용자에게 노출하지 않는다. `403`·권한 관련 `404`는 갱신 대상으로 보지 않는다.
- **중복 방지:** 생성·참여·편집 명령은 고유 요청 ID를 사용한다. 같은 계정·행동 범위에서 같은 ID와 같은 내용은 한 번만 반영하고, 같은 ID의 다른 내용은 거절한다. 응답이 유실되면 같은 ID로 재시도한다. 요청 기록에는 저장 결과 식별자·버전만 남기고 재응답 때도 현재 권한을 확인한다. 클라이언트 초안 보관 기간과 요청 기록의 유효 기간을 함께 정해 만료된 모호한 요청을 자동 재실행하지 않는다.
- **동시 추가와 수정:** 추가는 날짜 문맥을 구조 버전으로 확인한 뒤 해당 날짜의 끝에 넣는다. 같은 날짜에 추가가 겹쳐도 순서 버전만 다르다는 이유로 거절하지 않으므로 두 방문을 모두 보존한다. 수정은 바꾼 필드와 기준값을 검증한다. 시간과 메모처럼 겹치지 않는 변경은 합치고, 같은 필드나 이미 변경된 날짜 문맥을 바꾸려 하면 최신 내용과 충돌 범위를 돌려준다. 입력하지 않은 필드와 명시적으로 지운 값을 구분한다.
- **순서와 기간:** 재정렬은 구조 버전·해당 그룹의 기준 버전·방문 ID를 확인한다. 날짜 이동은 기존 그룹과 대상 그룹을 함께 갱신한다. T05의 `적용`은 시각·메모·날짜·순서의 수정안을 한 명령으로 보내고 검증에 실패하면 일부만 저장하지 않는다. 충돌은 `409`로 처리하고 재적용은 최신 상태에서 새 요청 ID로 보낸다. 단순 시간 수정은 자동 재정렬하지 않는다.
- **삭제와 회복:** 삭제된 방문에 들어온 일반 수정은 복구·복제를 만들지 않는다. 되돌리기는 본인의 원래 작업을 참조하는 별도 명령이다. 허용 기간과 현재 권한·후속 변경을 확인한 뒤 적용하고, 다른 사람이 수정한 결과를 덮어쓰지 않는다. 필요한 복원 정보만 짧게 보관하고 기존 스낵바에 버튼이 있다고 가정하지 않는다.

초대 비밀값은 추측하기 어렵게 발급하고 서버에는 검증에 필요한 해시와 만료·철회 상태를 보관한다. 7일은 제품 명세의 제안이며 설정값으로 둔다. 참여는 로그인과 명시적 선택 후 같은 트랜잭션에서 확인한다. 멤버 제외 시 기존 초대를 무효화한다. 계정 삭제는 회원·관리자 진입 모두 여행 정리를 거친다. 본인 탈퇴는 소유권 수락 또는 삭제가 필요한 여행을 먼저 해결하고, 관리자 경로에서 강제 정리해야 할 경우의 정책은 P4 착수 때 정한다. 공동 방문은 유지하고 제거된 회원의 표시 정보와 변경 기록은 출시 전에 정한 보관 정책으로 처리한다.

## 6. 모바일 화면·상태·저장 처리

| 상태 | 보관 주체와 원칙 |
| --- | --- |
| 서버가 확정한 계획 | 저장소가 여행·계정 범위의 최신 스냅샷과 순번을 관리한다. 순번이 낮은 응답으로 최신 상태를 덮지 않는다. |
| 현재 보기 | 선택 일차·방문·시트 모드·카메라·스크롤은 공동 데이터와 분리한다. 계정과 여행에 묶어 마지막 유효 날짜를 복원하며 명시적 진입 대상이 먼저다. 카메라 이동 자체는 저장 명령이 아니다. |
| 수정 중 입력 | 편집 시트의 초안, 기준값·버전, 이미 제출한 요청 ID를 분리해 보관한다. 새 서버 스냅샷이 와도 초안을 덮지 않는다. 확정과 동기화 지연·오류·충돌을 각각 상태로 표현한다. |
| 입력·저장 복구 | 네트워크 실패와 응답 유실을 구분할 수 없으면 같은 요청 ID로 결과를 확인한다. 재연결 시 현재 계정·권한·최신 계획을 확인한 뒤 재시도한다. 오래된 요청을 다른 계정의 자격으로 보내지 않는다. |

`ViewModel`은 `viewModelScope`에서 작업을 관리하고 읽기 전용 `StateFlow`로 상태를 공개한다. `Route`는 `collectAsStateWithLifecycle()`로 수집하고 화면 콜백을 연결한다. `Screen`과 지도·방문 행은 불변 상태를 렌더링한다. 같은 `selectedVisitId`와 날짜 목록으로 핀·번호·연결선을 파생한다. 지도 SDK 객체와 대형 결과 응답을 `UiState`에 넣지 않는다. 행은 방문 ID로 안정적으로 식별하고, 메모 입력 한 글자마다 지도 마커·선 전체가 다시 만들어지지 않는지 확인한다.

- **검색:** 검색어·도시·지도 범위를 키로 삼는다. 새 키가 오면 이전 작업을 취소하고 새 요청을 짧게 지연한다. 빈 입력·화면 닫기에서 요청을 끝낸다. 응답이 늦게 도착해도 현재 키와 다르면 표시하지 않는다. 취소는 일반 오류로 처리하지 않는다.
- **편집:** 드래그 중에는 위치 미리보기만 바꾸고 놓았을 때 한 번 저장한다. T05는 `적용`에서 저장한다. 빠른 중복 탭이나 같은 여행의 구조 변경은 제출 상태로 제어하고, 처리하지 못한 입력은 초안에 남긴다. 최신값만 보관하는 Flow에 저장 명령을 흘려 보내지 않는다. 목록의 미리보기와 서버 확인 후 `저장됨`을 구분한다.
- **동기화:** 첫 안은 열린 여행 한 건에 대한 조건부 조회다. 가시 화면과 앱 포그라운드에서만 돌리고 화면 종료·로그아웃·접근 종료 시 멈춘다. 앱 복귀·재연결·내 저장 완료 시 최신 상태를 확인한다. 요청을 겹쳐 보내지 않고 실패 시 간격을 늘린다. 내부 베타에서는 5초 간격을 출발점으로 지연·요청량을 재고 조정한다. 목표 지연을 충족할 수 없으면 조회 계약을 유지한 채 SSE 등 갱신 신호를 검토한다. 친구의 편집은 카메라·선택 일차·입력 포커스를 움직이지 않는다.
- **기기 보관:** 허용된 사용자 작성 내용과 미전송 초안만 계정별로 보관한다. 플랫폼 보호 저장소와 만료·삭제 정책을 확인한 뒤 사용한다. 읽기 가능한 마지막 확인 데이터와 미저장 초안을 표시상 분리하고, 오프라인에서 신규 구조 변경을 확정하지 않는다. 권한 철회·로그아웃·계정 전환을 확인하면 해당 데이터와 요청을 정리한다. 오프라인에서는 철회를 즉시 알 수 없으므로 보관 만료·재인증 기준이 확정되기 전 비공개 데이터를 오래 노출하지 않는다.

## 7. 진입·지도·알림 연동

### 기존 화면과 인증 복귀

`MainNavigator`에 내 여행·생성·여행·초대 확인의 타입 안전 경로를 추가한다. 도시/기간 상세는 확인된 도시 ID와 추천 기간만 전달하고 T02에서 실제 날짜를 편집한다. 날짜·여행 ID 같은 참조만 라우트에 둔다. 메모·전체 일정·초대 비밀값은 라우트 인자나 로그에 두지 않는다. 로그인 없이 입력한 생성 초안과 인증 필요 의도는 임시 보관하고, 완료된 인증 세션에서 원래 화면을 한 번만 복원한다. 인증 취소는 입력으로 돌아가고, 가입·연차 설정 건너뛰기도 같은 복귀를 사용한다. 기존 홈 진입과 성공 스낵바는 플래너 복귀를 방해하지 않아야 한다.

홈 이어보기는 별도 요약 조회로 연결해 오류가 홈 추천을 막지 않게 한다. 진행 중 → 내가 마지막으로 연 예정 여행 → 가까운 출발 순서 등 통합 명세 4.2의 선택 규칙을 따르고, 내 열람 기록과 타인의 수정 시점을 섞지 않는다. 지난 여행의 다음 휴가는 현재 연차 설정의 기존 캘린더로 보낸다. 플래너와 초대 흐름은 하단 탭·방해 광고를 숨긴다.

### Google 지도·장소와 외부 링크

- Android·iOS 공식 지도 SDK를 감싼 플랫폼별 화면을 우선 검증한다. 공통 화면은 핀·선·선택·카메라 이벤트 계약만 갖는다. KMP 래퍼를 선택할 경우 두 플랫폼의 지도 출처, 제스처, 생명주기·해제, 다크 테마, 핀 선택, 목록 시트와의 조작을 먼저 비교한다. 필요한 SDK·버전은 P0 결과와 빌드 호환성으로 정한다.
- 장소 검색은 서버의 Places 조회를 우선안으로 둔다. 장소 ID와 화면에 필요한 이름·주소·위치만 요청하고, 사용자 작성 값과 공급자 표시용 값을 분리한다. 장소 ID 외 공급자 값의 보관 조건은 API·계약별로 확인하고 응답 전체를 저장하지 않는다. 사용자 직접 입력으로 둔갑시켜 복제하지 않는다. 이름을 새로 조회할 수 없을 때 작성 제목 또는 중립 라벨로 방문·시각·메모를 계속 표시한다. [Places 정책](https://developers.google.com/maps/documentation/places/web-service/policies)·[요청 필드 선택](https://developers.google.com/maps/documentation/places/web-service/choose-fields).
- 모바일 지도 키와 서버 검색 키는 환경·용도별로 분리·제한한다. 키를 코드·문서·로그에 넣지 않는다. 지도·검색·상세 사용량을 각각 제한하고 출처 표시는 시트와 결과 영역에서 가리지 않는다. 지도/검색에 실패해도 계획 API와 직접 추가는 동작한다. 번호와 선은 방문 순서만 표현하며 좌표가 없는 곳에서 끊는다. 실제 길찾기는 [Maps URLs](https://developers.google.com/maps/documentation/urls/get-started)로 열고 선택 일차를 보존한다.
- 초대는 [Android App Links](https://developer.android.com/training/app-links/about)·[Apple Associated Domains](https://developer.apple.com/documentation/xcode/supporting-associated-domains)로 검증된 HTTPS 호스트를 사용한다. Android `MainActivity`와 iOS 호스트에서 초기 실행·실행 중 링크를 수신하고, 새 초대만 별도 허용 경로에서 해석한다. 설치 전 웹에서는 제한된 안내와 스토어 연결을 제공한다. 설치 뒤 원래 링크 다시 열기를 보장 경로로 검증한다. 자동 복귀는 확인된 환경에서만 지원으로 표시한다. 초대값이 주소·리퍼러·접근 로그·분석으로 전파되는지 확인하며, 가능하면 URL 조각을 쓰되 양 플랫폼·메신저에서 보존되는지 검증한다.

### 개인 알림

출발 전 알림은 더보기에서 사용자가 직접 켤 때만 권한을 요청한다. 다른 기기의 변경으로 예약이 취소돼야 하므로 서버 예약·검증 발송을 우선한다. [Firebase Cloud Messaging의 iOS 연동](https://firebase.google.com/docs/cloud-messaging/ios/get-started)은 후보이며, 기존 Firebase 설정·브리지가 곧 발송 지원을 뜻하지 않는다. P6에서 Android·iOS 권한·토큰·발송 자격 증명을 확인한다.

예약은 회원·여행별로 관리하고, 신청한 기기를 수신 대상으로 기록한다. 예약 해제·기간 변경·멤버 제외·삭제는 이전 예약을 무효화한다. 기기 로그아웃이나 계정 변경은 해당 기기의 수신 연결을 해제한다. 발송 작업 확보와 실제 공급자 인계 시작을 구분한다. 인계를 시작할 때 예약 버전·권한·대상 기기를 확인하고, 취소와 인계 시작 중 어느 쪽이 먼저 확정됐는지 기록한다. 취소가 먼저면 이미 큐에 있던 작업도 발송하지 않는다. 예약 버전당 중복 인계를 막고 결과가 불명확할 때 같은 알림을 무조건 다시 보내지 않는다. 이미 공급자에게 넘긴 알림은 회수를 보장할 수 없으므로 인계 직전·직후 취소를 각각 테스트하고, 알림을 열 때도 최신 상태를 조회한다. 잠금 화면에는 여행 제목·일정·동행자·메모를 기본 노출하지 않는다.

**검사 실행:** 현재 [서버 CI](../.github/workflows/backend-ci.yml)는 `:server:bootJar`, [Android CI](../.github/workflows/android-ci.yml)는 `:composeApp:assembleDebug`를 실행한다. 구현 시 서버 `:server:test`, 양 모듈 `ktlintCheck`, 모바일 공통 테스트가 포함되는 Android·iOS 타깃 테스트, iOS `iosApp-Debug` 시뮬레이터 빌드를 추가 확인한다. 실제 Gradle 테스트 태스크는 `./gradlew :composeApp:tasks --all`로 확인해 CI에 연결한다. 빌드만 성공한 상태를 테스트 통과로 보지 않는다.

**운영 검증:** 서버 응답·앱 노출은 기존 버전과 호환되도록 확장한다. 비파괴 migration → 서버 배포 → 앱 테스트 배포 → 제한된 공개 순서로 진행하고, 이상 시 진입·새 쓰기·초대·발송을 필요한 범위에서 중지할 수 있게 한다. 데이터 삭제나 역 migration을 기본 복구로 사용하지 않는다. 초기 운영 상한과 동기화 간격은 베타에서 기록한 요청량·응답 시간·DB 경합·기기 반응으로 정한다. 지도 쿼터 초과 때도 사용자 작성 계획은 열 수 있어야 한다.

**리텐션과 개인정보:** 통합 명세 14장의 생성·첫 날짜 배정 저장·의미 있는 재사용·협업·다음 여행을 같은 정의로 집계한다. 저장 확정과 단순 화면 노출을 분리하고, 같은 요청의 재시도를 성공으로 중복 집계하지 않는다. 앱 실행·알림 열기만으로 재사용을 판정하지 않는다. 이름·제목·메모·검색 원문·초대값·개인 연차는 이벤트 속성으로 보내지 않는다. 새 화면의 녹화 차단 또는 검증된 가림을 화면 노출 전에 적용한다. 플랫폼별로 보장할 수 없으면 해당 베타의 리플레이를 끄고 확인한다. 정식 리텐션 효과는 구현·관찰 전에는 알 수 없다.

## 9. 작업을 시작할 때와 끝낼 때

- [ ] `guide`의 제품·디자인 명세와 대상 AC를 읽고 이번 변경에서 검증할 한 가지 사용자 흐름을 고른다.
- [ ] 현재 빌드·테스트 기준선을 확인한다. 외부 설정이 없는 검증은 미확인으로 남기고 재현 가능한 테스트 환경을 적는다.
- [ ] 서버 계약과 저장 규칙을 확정한 뒤 모바일까지 연결한다. Kotlin 공개 타입을 명시하고 문자열은 네 언어 리소스에 둔다.
- [ ] 권한·중복·취소·입력 보존의 실패 사례와 기존 오구리의 흐름을 확인한다. 정상 사용자에게 새 단계가 늘어났다면 명세의 가벼운 사용감 기준으로 바로 수정한다.
- [ ] P7에서 AC01–AC22와 실제 기기 과업을 대조한다. 기능 누락, 기존 흐름과의 단절, 재사용 가치가 약한 곳을 보완하고 해당 사례를 다시 실행한다.

이 문서에서 확정한 것은 작업 순서와 계약의 방향이다. 지도 SDK·초대 도메인·보관 기간·운영 한도·발송 공급자는 각 단계의 검증 결과로 결정한다. 이번 변경은 구현 계획 문서 추가이며 앱 코드·DB·외부 서비스 설정을 변경하지 않는다.
